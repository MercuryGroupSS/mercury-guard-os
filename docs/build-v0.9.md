# Mercury Guard OS v0.9 — signed shift-grant validation foundation

Adds a transport-neutral staging grant verifier and a verified-grant action gate. The installed app remains demo-only: no production issuer/trust key, enrollment, guard identity, authenticated time source, grant persistence or network transport is configured. DemoSession never consumes this verifier; existing operational buttons still use the explicitly labelled local demo session. Device information states server authorization is disabled. This is security foundation code, not completed production authentication.

## Provisional staging envelope

The verifier accepts key ID, base64url payload and base64url signature as separate fields. Signature input is ASCII `mercury-shift-grant-v1.<keyId>.<payload>`. Algorithm is fixed SHA256withRSA, using trusted RSA public keys of at least 2048 bits and platform [Signature](https://developer.android.com/reference/java/security/Signature). It accepts no algorithm selector, embedded key or remote key URL. Base64url is unpadded and canonical. Payload is limited to 16,384 encoded characters and must round-trip exactly through compact Android JSONObject encoding; duplicate/unknown claims, trailing text and numeric coercions are rejected. This provisional envelope is not JWT/OIDC and requires independent protocol review/interoperability vectors before service integration.

Exact payload fields: `version` (integer 1), `grant_id`, `issuer`, `audience`, `guard_id`, `site_id`, `assignment_id`, `device_thumbprint` (lowercase SHA-256 hex), `revocation_version` (nonnegative integer), `issued_at_ms`, `not_before_ms`, `expires_at_ms` (integer epoch milliseconds), and `actions` (unique nonempty list drawn from patrol, incident, photo, check_in, location). Strings are nonblank and at most 256 characters. Issuer/audience and the complete guard/site/assignment/device/revocation binding must match independently supplied expected values. Expected values must never be copied from the untrusted token.

The initial provisional grant lifetime is capped at 15 minutes. Issued time <= not-before <= trusted current server time < expiry. An authenticated server-time anchor is paired with elapsed realtime and boot count by a future trusted transport; this validator cannot authenticate an anchor supplied by its caller. No device wall-clock API is used. Verified permissions expire using the remaining monotonic lifetime, reject clock rollback/reboot, require the unchanged binding/revocation version and deny unspecified actions. A changed context/version invalidates the grant locally. There is no live revocation fetch, replay registry, attestation, device proof-of-possession or server authorization enforcement yet. Revocation while offline is bounded only by grant expiry after a future integration enables grants.

Test signing keys are generated at test runtime and are not installed as trusted app keys. Empty/unknown key trust rejects grants. No existing apps/repositories, phone state, cloud resources or credentials are changed. White Jarvis-inspired styling remains deferred.

Validation pending: six unit tests and thirty-one instrumented tests on each API 28 and 35, build, lint and signature verification. Physical Fold6 testing, production signing and authenticated staging integration remain pending.
