# Mercury One v0.35 — attended Galaxy Z Fold6 acceptance

This is a test plan. Every v0.35 Fold result starts **OPEN**; earlier [v0.23 demo results](fold6-physical-v0.23.md) do not establish connected-account, delivery or continuous-location acceptance.

## Before touching the phone

- Record APK version/package, signing identity, source commit and SHA-256. Preserve the approved Preview installation, keys, queues and drafts. No uninstall, storage clear, reset, key replacement, other-app changes or global security/permission changes. An incompatible update blocks testing.
- Require phone-reachable **HTTPS** with approved pinned issuer configuration. Unconfigured builds cannot run connected tests; emulator `localhost` trust and `.httpstest` packages are not Fold provisioning.
- Prepare synthetic **Guard A/B** with different individual Guard IDs/Auth subjects and one shared company Vendor ID; approve this installation/site and each guard's assignments. Explicitly provision rounds/checkpoints, any check-in policy, and assignments with/without location policy. Do not infer identities from payroll/vendor records.
- Owner attends fingerprints, folding and unlocking; allow for the roughly ten-minute phone lock. Keep evidence private, respect screenshot protection and exclude credentials/private keys or published real coordinates/photos.
- Approve the exact synthetic notice, cadence, accuracy/freshness limits, lease and optional geometry. Require an approved operator and isolated receiver; a projection helper is not receiver delivery.

With a valid trusted service configuration, launching Mercury One opens the account/enrollment flow directly. The unconfigured Preview can open **Prototype tools → Guard account connection**, but that entry only reports missing configuration and cannot perform these connected tests. Demo **Request GPS for active demo shift** and readiness tracking are separate from connected collection.

## Missed clock-out regression

With separately approved short synthetic schedules, let assignment A's scheduled end pass without clocking out. Record that its attendance remains unclosed and the app labels the elapsed window honestly; no new capture or automatic attendance end is allowed. At or after that boundary, start approved assignment B. A's unresolved end request must not conceal B's service-approved start. A conflicting live guard/device start must still fail.

While B has its own explicitly consented collector/reminder, explicitly close A within its permitted late-close window. Confirm only A closes and B's matching notification/collection/reminders continue. Do not change phone time or production schedules to force this case. End B explicitly, then sign out and verify all connected collection/reminders/upload authority stop. Original A/B records and receipts must remain distinguishable. This physical regression starts **OPEN**; backend and emulator results do not establish the Fold result.

## Evidence and acceptance boundary

Backend/real-Auth/HTTPS checks prove scope/nonce rollback, immutable retries, separate media receipts and consent barriers. Earlier emulator HTTPS account/patrol/photo/Escalate checks passed. The retained v0.34 baseline passed six encrypted draft-store tests, actual Activity lifecycle recovery and visible location consent/service/renewal/withdrawal. Its separately labelled typed 0,0 fixture passed the production filter/store/proof and real Auth/PostgreSQL HTTPS; actual SDK GPS delivery remains unverified because the emulator produced no platform fixes. Consult the exact package record for terminal CI and final counts. None proves Fold biometrics, camera/GNSS, cover-screen behavior, audible alerts, doze or endurance. Every physical step remains OPEN/BLOCKED until observed. Close with no active test shift/collector or signed-in account; preserve app data.

For each issue retain the build SHA, private test IDs, expected/observed state, time and relevant receipt IDs. An unavailable GPS fix or delayed Android job is not a pass; a generic error is not proof that an earlier request failed to commit.

## Approved inputs and deployment gates

Operational gates: approved identities/vendor links/enrollment; reachable HTTPS/key distribution; schedules/routes; optional location notice, retention, cadence, uncertainty/lease limits and geometry; operator coverage/response rules and separately approved contacts; private media/backups; and live data-exchange authorization. No production cadence, geometry or contact is invented here. Require attended Fold, connectivity recovery and full-shift battery/doze evidence. Managed-device/kiosk and flashable-OS work is separate; no firmware/device-management changes are part of this test.
