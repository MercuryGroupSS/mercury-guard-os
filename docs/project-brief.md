# Mercury One — current project brief

Updated 23 October 2026. The product is still in development. This brief describes the current state; the [complete development history](development-history-through-shared-delivery.md) and internal cumulative baseline remain preserved.

## Accepted scope

Deliver an ordinary native Android app for Galaxy Z Fold6, preserving Pixel portability. Use individual guard identities even when one Vendor ID represents a company employing several guards. Keep biometric handset unlock distinct from proof of a named guard. Integrate assignments and observations with Mercury Ops through explicit mappings. Develop dedicated-device management and firmware feasibility separately after the APK track.

Work is confined to MercuryGroupSS/mercury-guard-os. Existing applications and repositories are unchanged. Hosting charges were deferred in favor of isolated local Supabase tests. Current physical-device testing is deferred.

## Backend now implemented and locally verified

PostgreSQL mode shares vendor/guard identities, approved device keys, assignments, Ops mapping approvals, confirmed shifts and idempotent transition/rejection receipts. It also shares capture grants, signed event/evidence records, check-in deadlines and scheduler state, dispatch versions/cursors, outbound mappings/history, queue leases/receipts and projection cursors. The local runner now defaults to PostgreSQL; SQLite remains an explicit synthetic protocol mode. Existing SQLite records are not automatically migrated by selecting PostgreSQL.

Auth tokens are verified remotely. Vendor/company identity does not substitute for individual guard authentication. Current roster, device, assignment and grant state is rechecked at operational commit boundaries. Revoked access cannot recover a receipt to bypass authorization.

The [administration console and API](administration.md) now support explicitly approved Auth administrators, bounded catalogs, reviewed reasoned mutations and append-only transactional audit. The white/cyan console can manage vendor/site status, link existing individual Auth accounts, approve/revoke devices and mappings, and publish scoped dispatch versions. Unconfirmed requests retain their exact ID/body and can resolve to the original receipt or a permanent not-applied closure. An owner-only local command provisions/revokes membership for a confirmed individual account with an atomic access-audit receipt. The console shows current administrators and access history. Personal account setup/recovery now verifies an emailed code, sets the user's password, and signs out sessions without returning tokens or granting roles. Real email transport and owner activation await configuration and the selected identity. No real administrator was activated during these tests.

Local Auth now requires email confirmation, a 12-character minimum password and 8-digit ten-minute codes. Mailpit captures local test messages only. A scoped startup helper enforces and inspects localhost-only published Docker ports, preserves volumes on restart, and stores runtime credentials privately. Existing hosted services, applications and global Docker/Mac network settings remain unchanged.

PostgreSQL requests now verify the token remotely and require its exact current Auth session to exist for the same individual subject and remain unexpired. Provider sign-out denies the old token immediately at the next Guard/admin request, independently of JWT expiry. The session reader uses three metadata columns; its new grants include no refresh credentials or Auth mutation rights. An already-authorized transaction may finish across a concurrent provider sign-out.

Recurring Ops reads are opt-in and use only explicitly approved shift IDs. Live reading/sending is not enabled. Isolated inbox receipts prove stored integration records; they do not prove actual Ops rendering or payroll updates. Private byte transfer is verified separately below.

The [PostgreSQL observation receiver](dashboard-receiver.md) now has an independent private schema, owner-approved mapping ledger, immutable observations and receipts. It rechecks receiver authorization inside the storage transaction, including exact retries. The HTTP handler awaits commit before acknowledging. The sender now supports opt-in destination-specific HTTPS endpoints/credentials; default sending stays off, unknown destinations are rejected before transmission, and synthetic SQLite mode cannot enable delivery. Separate-database and actual process/CLI tests passed. No live destination was enabled.

Private photo bytes now have their own durable receiver receipt and sender retry/lease state. Transfer waits for accepted photo metadata, available source bytes and the original active mapping. The destination rechecks its approval at byte commit and preserves exact retries without replacement. Separate-database and actual receiver-process HTTP checks verified stored bytes, restart recovery, false-receipt/stale-lease denial and revocation during upload. Protected received-report rendering and private JPEG display are now implemented and locally verified. Real camera-image acceptance and actual Ops integration remain open; sending is still disabled without explicit HTTPS destination configuration.

The protected Reports console now presents original observations and separate media receipts, with authenticated private JPEG viewing. Exact-scope linkage, hash/length checks, bounded precise pagination and transactional current administrator checks passed. Browser testing decoded a synthetic JPEG and confirmed that revocation and explicit sign-out clear the image. Explicit sign-out now revokes the exact provider session, including for an inactive guard/admin, while preserving independent sessions.

The native automatic-delivery continuation is implemented and passed actual scheduled HTTPS integration verification. It uses encrypted short-lived guard/device/config-bound upload authority, network-constrained scheduled work, immutable original-scope pending snapshots and explicit sign-out cancellation. Expired/rebooted authority requires sign-in. This remains separate from Android's scheduling guarantees and physical Fold acceptance; see [automatic delivery notes](android-automatic-delivery.md).

Approved patrol routes now support explicit named rounds. Checkpoints remain selectable in any order within each declared round; the same checkpoint can be repeated across authorized rounds. The immutable policy, guard/assignment/route revision/round/checkpoint key prevents same-round duplicates across grants, restarts and devices. Legacy routes retain their original single-pass shape. PostgreSQL migration/replay and native JVM/UI/store/scheduled HTTPS checks passed. Console route approvals and historical report details preserve the original round ID. See [patrol rounds](patrol-rounds.md).

A separate [operational escalation inbox](escalations.md) now accepts immutable intent-bound device signatures before, during or after an assignment, with a currently authenticated individual guard. Optional GPS never substitutes for identity or blocks an absent fix. The private operator queue records an explicit first acknowledgement and guard-visible response, sharing existing exact administrator request IDs/audit and permanent not-applied resolution. Current session/guard/vendor/device/site rechecks, nonce rollback, proof replay/cross-scope denial, concurrent acknowledgements, audit rollback and bounded pagination passed in disposable PostgreSQL. Real local Auth/HTTP and rendered browser checks now pass for intake, exact retry, role/site/guard/session revocation, operator acknowledgement/audit and originating-device status. The native escalation UI/queue is being completed; no external dispatch contact or notification is enabled.
