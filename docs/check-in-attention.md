# Optional connected check-in attention — v0.43 candidate

This candidate brings the previously recorded calm alert design into the individually signed-in workflow. Its acceptance requires the exact-source CI and immutable configured package records. The accepted baseline is v0.42; physical Fold testing remains deferred.

An administrator may explicitly select the calm progressive preset while reviewing an Ops assignment binding. The existing policy revision and approval history retain the complete choice. The optional extension is exactly `attention: {version: 1, profile: "calm_progressive_v1"}`. A malformed present extension is rejected. Omission preserves the existing normalized policy and one-cue behavior. No post is enabled automatically, and no universal check-in cadence is introduced. Enable this profile only after the compatible client is accepted and installed.

The profile starts green, becomes yellow after two minutes and red after five. Logical cue opportunities occur at 30-second offsets, with at most twenty attempts and no replay burst after delay or restart. Every opportunity is clipped to the actual approved response window and shift end. Ending the ten-minute cue budget does not close a longer response window or create a missed check. A calm four-second pulse has steady and system reduced-motion alternatives. The existing approximately 650-millisecond chime and bounded vibration are used through a separate channel; existing channel choices remain preserved.

Attempt high-water marks, silence and the current-slot token are encrypted under the original configuration/device/individual/assignment/policy/slot. A swipe or Silence quiets only that window. Local completion is reconciled against the exact original owner's captured check-in proof, with an isolated index and encrypted outer attribution. Legacy or differently owned events cannot silently count as the current individual's completion. The event wire shape, original retry identities and biometric/GPS/consented-photo requirements remain unchanged. A local save remains distinct from a service receipt.

The connected private view retains the current account, session, key and screen fences. A generic alert surface contains no guard/site identity or credentials. Optional full-screen presentation requires explicit local opt-in, current Android eligibility and a valid current-slot token. It never dismisses keyguard or starts an activity directly from the background. Opening private details requires fresh user-initiated sign-in; live foreground account screens are locked and scrubbed while original drafts, pending photo output and queues remain preserved. Opening another account window preserves photo output still owned by a live window; abandoned output remains eligible for cleanup. This preserves the file without extending its original capture authority.

Android controls background delivery. Even idle-capable alarms are rate-limited in Doze, so a 30-second logical cue opportunity does not guarantee a notification every 30 seconds. See [Android Doze restrictions](https://developer.android.com/training/monitoring-device-state/doze-standby). Existing channel settings belong to the user; the app preserves them rather than replacing their behavior. See [notification channels](https://developer.android.com/develop/ui/compose/notifications/channels). Full-screen permission may be unavailable on Android 14 and later; denied access falls back to normal notification behavior. See [full-screen eligibility](https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent()) and [time-sensitive notifications](https://developer.android.com/develop/ui/views/notifications/time-sensitive).

Generic future-window reminders retain their existing ability to outlive a short capture grant. They authorize no evidence collection. Actual capture still requires current authority. Sign-out, explicit disable, configuration/key/account switch and the original assignment end stop the corresponding schedule. Older unmarked ownerless reminder state is preserved without adoption and requires fresh individual enablement.

Required acceptance includes exact stage/window boundaries, maximum cue attempts, restart without catch-up, owner isolation, legacy preservation, silence without completion, original-owner photo/check-in capture, channel preservation, reduced motion, valid/stale token actions and rapid alert return without recovering private authority. Actual cue timing, full-screen delivery, camera/GNSS, fold behavior and full-shift battery/Doze remain attended-device gates. No email, SMS, external dispatch, new live assignment or firmware action is part of this feature.
