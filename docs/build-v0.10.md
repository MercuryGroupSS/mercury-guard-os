# Mercury Guard OS v0.10 — local installation identity and enrollment proof foundation

Adds an explicitly created installation signing key under Android Keystore, separate from local-data encryption and APK signing. Device information offers a confirmation before creation and displays the SHA-256 fingerprint of the X.509 SubjectPublicKeyInfo public key. Viewing information does not create keys. Key generation runs off the UI thread. The key uses P-256 / SHA256withECDSA. Private key bytes are not exported; software/hardware backing, attestation and device integrity are unverified. See [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

A no-backup atomic public-fingerprint marker checks continuity. A missing signing key, missing marker for an existing key or changed fingerprint fails closed; code does not silently generate a replacement. The marker is not a server enrollment record or protection against a compromised app/OS. A failure between key generation and marker completion can require administrator recovery; no reset/rotation/recovery UI is implemented. Uninstalling or clearing app data can lose installation identity. Production needs authenticated recovery and key rotation.

A transport-neutral enrollment proof signer accepts a 32–64 byte canonical unpadded base64url server challenge, lowercase canonical UUID request ID, and restricted ASCII audience. It signs ASCII `mercury-enrollment-proof-v1\n<audience>\n<requestId>\n<challenge>\n<deviceThumbprint>` and returns a provisional version-1 JSON proof containing the public SPKI, fingerprint and unpadded base64url DER ECDSA signature. It is not JOSE raw R||S encoding. No generic arbitrary-message signing API or UI challenge importer is exposed.

The future server must independently validate the public-key fingerprint, signature, audience, challenge ownership/expiry/single-use state, inventory enrollment and guard/device policy. Client signing alone does not prevent replay, prove user identity, establish key hardware backing, or approve enrollment. Audience and challenges must originate from an authenticated configured service; the signer cannot authenticate its caller's inputs. No live server, issuer, credential, key attestation, enrollment, event signing, grant enforcement integration or transport is enabled. Existing demo behavior remains unchanged and sends nothing.

No existing apps, other repositories, cloud services or phone-management state are changed. White Jarvis design is deferred. Stable APK release signing remains separate and pending.

Validation pending: six unit tests and thirty-six device tests on each API 28 and 35, build, lint and signature verification. New tests cover explicit initialization, persistence, non-exported private-key bytes, public fingerprint, challenge signatures/context binding, malformed inputs, missing/mismatched key continuity and the confirmation UI. Physical Fold6 hardware/attestation testing remains pending.
