# Mercury Guard OS v0.12 — encrypted incoming assignment/dispatch cache

Adds a transport-neutral receive cache for versioned assignment and dispatch records, separate from the outgoing audit queue. There is no live connection, import UI, server authentication, grant enforcement integration or execution of incoming commands. Device information explicitly says inbound sync is disabled. A future authenticated transport must validate identity, server, grant and scope before calling this storage boundary.

The provisional page has exact fields schema_version (integer 1), scope, previous_cursor, next_cursor and changes. Scope must exactly match independently supplied guard/site/assignment/device/revocation bindings. Each change has exact fields id (canonical UUID), version (positive integer), type (assignment or dispatch), deleted (boolean) and data (JSON object). Tombstones require empty data and retain ID/version to reject stale resurrection. Existing IDs cannot switch type, regress version or change content at an unchanged version. Duplicate IDs within one page are rejected. A newer version may explicitly restore a tombstoned record.

Changes and next cursor commit in one SQLite transaction; any validation, encryption or database failure rolls back both. The most recently committed page can be replayed as a no-op; canonical JSON comparison tolerates property-order changes. Other stale/mismatched cursors fail. Cursor-reset/full-snapshot reconciliation remains a future explicit protocol; the client never silently skips forward. Pages are limited to 100 changes and 256 KiB serialized input. Cursor strings are bounded printable ASCII; next cursor must be nonempty and different from previous, including on empty pages.

Records/cursors are encrypted with purpose/context-bound AES-GCM under the existing local data key. Scope hashes and record UUIDs remain visible metadata; hash inputs are not a secret identity protection. Ciphertext moved across IDs/scopes fails authentication. Existing stored data is not erased on failure. Queries read bounded rows; tombstones are hidden by default but retained. Production retention, old-scope cleanup, large-cache management, key recovery and guard identity separation at the UI remain unresolved. No inbound cache is surfaced to the demo operational UI yet.

This is a foundation for the confirmed two-way integration requirement: receive authoritative business instructions and send signed observations through a restricted API with server adapters. No existing app/database, staging branch, cloud resource or credential was modified. The previously observed unrelated staging migration failure was not changed. White Jarvis UI, stable APK update signing and physical Fold6 validation remain pending.

Validation pending: six unit tests and forty-seven device tests on each API 28 and 35, build, lint and signature verification. New tests cover encrypted reopen/scope isolation, canonical replay, versions/tombstones, conflicts, transactional rollback/retry, ciphertext relocation, malformed/stale/oversized pages and unchanged cursors after failure.
