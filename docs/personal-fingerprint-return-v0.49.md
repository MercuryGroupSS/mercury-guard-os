# Personal fingerprint return sign-in, v0.49

After first verifying the individual guard's ID and password, an administrator-approved personal phone can opt into fingerprint return sign-in. The sign-in form has an explicit personal-setup checkbox. Shared site phones keep individual sign-in for every guard and cannot obtain the personal credential. A company vendor ID never identifies a person.

The Android store uses a separate Android Keystore RSA private key requiring a fresh strong biometric for each decryption. New biometric enrollment invalidates this key. A random AES-256 GCM key encrypts the return credential, then RSA OAEP wraps that data key. Public-key wrapping allows rotation after one fingerprint without a second biometric operation. The envelope is atomic, excluded from backup, and bound to the packaged service configuration and existing installation-key fingerprint. No password is retained. The original installation signing key and encrypted shift records are preserved. The sign-in activity remains FLAG_SECURE.

The server exchanges passwords and refresh credentials only with the configured Auth origin over verified transport. The new personal routes independently check the exact individual, vendor, approved personal device, installation proof, revocation version and current provider session. An issuer-signed, domain-separated permit binds those values, the service origin, and the hash of one refresh generation. Permits expire 30 days after initial setup; renewal does not extend that deadline. Existing site/admin password endpoints still exclude refresh tokens.

Initial setup requires a signed installation proof no older than 60 seconds and the actual account password. A replay of that initial request still requires the password-bearing request; it cannot substitute an account, device, or personal approval. Return sign-in uses a fresh server nonce, a distinct signature domain binding the exact permit and refresh hash, and one-time nonce consumption. Auth independently rotates the refresh credential. Its documented parent-token recovery permits a safe retry if the response was lost. A new encrypted envelope is committed before exposing the foreground session. Generation checks prevent a late refresh from restoring an explicitly forgotten account.

Revoked sessions, inactive or ambiguous individuals, vendor deactivation, mode/guard changes, key changes and device revocation deny return sign-in. The checks bracket asynchronous Auth work. They do not serialize a later external Auth deletion after the final read with response delivery, matching the existing current-session policy. A transient network/provider failure preserves the encrypted credential for a new fingerprint retry; definitive denial removes only that saved generation.

Sign-out forgets the personal store and stops automatic uploads while retaining encrypted records. Provider sign-out remains best effort when no current foreground access token is available or the service is offline. Losing local access does not assert that every historical provider session was remotely deleted. Administrators can revoke the device; Auth session controls remain enforced. Personal return sign-in requires network access and does not grant attendance, capture, background location, or dispatch authority on its own.

## Validation and remaining acceptance

The actual local Supabase Auth/TLS fixture verifies personal password setup, refresh rotation, the original parent credential's recovery after the normal reuse interval, nonce replay denial, generation binding, provider logout and device revocation, while preserving another valid session. It also verifies two individual guards at one company on a shared site phone, multi-site personal assignment scope, and that no attendance is created. Every disposable account, device, assignment, limiter bucket and credential is ownership-scoped and cleaned up.

Android tests verify issuer/service/installation/token tampering denial, a fingerprint-protected vault's inability to decrypt without authentication, and that forgetting it fences a stale rotation. An emulator without an enrolled fingerprint must refuse setup. A successful real fingerprint return through the new CryptoObject still requires an attended scan after approved personal enrollment and initial private account sign-in. Prior fingerprint success in v0.47 is evidence for that older prompt only. Hardware GNSS/camera checks and CI do not establish an authenticated live shift.

Sources checked before implementation: [Supabase sessions and parent-token recovery](https://supabase.com/docs/guides/auth/sessions), [Android biometric cryptography](https://developer.android.com/identity/sign-in/biometric-auth), and [Android biometric key invalidation](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setInvalidatedByBiometricEnrollment(boolean)). The current Supabase changelog's TLS cipher change was reviewed; no TLS or certificate verification was relaxed.
