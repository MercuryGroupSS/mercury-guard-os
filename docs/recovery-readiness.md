# Local logical recovery drill

`node server/scripts/check-local-backup-restore.mjs` exercises actual PostgreSQL17 `pg_dump` and `pg_restore` against two newly created disposable databases. It accepts no arguments or remote database URL. It requires the private owned local stack configuration and the exact Guard database container, whose published port must be `127.0.0.1:55322`. It does not dump the running Guard database, start a service, call an Auth provider, change global worker/limiter rows, create production credentials or install an APK.

The source database receives the canonical migrations and minimal synthetic `auth.users`/`auth.sessions` dependency tables. The fixture creates an individual guard/vendor/site/device/assignment, an explicitly started shift, a signed capture grant and incident/photo observations. Sender and receiver mapping histories, original receipts, a pending delivery, retry attempts/leases and a real synthetic JPEG in both private media tables are included. The fixture has no real identities, password hashes, refresh tokens, mailbox messages or operational contact data.

The script creates an exclusive private ownership record before database creation. UUID-derived database names are never adopted. It writes a bounded custom-format archive into an owner-only directory and a mode600 regular file, then restores that archive into its empty second database with `--exit-on-error --single-transaction --no-owner`. ACLs remain in the archive; the existing cluster roles are not exported or modified. No `--clean`, `--create`, global dump or main-database restore is used.

Before allowing any post-restore mutation, it compares all fixture rows and original raw content, media bytes, sequence positions, constraints, indexes, RLS flags, owners, and effective schema/table/column/function/sequence ACLs. PostgreSQL's implicit default ACL is expanded using its object type and owner, and entries are sorted without dropping grantors, privileges or grant options. This equates an explicit owner-default ACL with its equivalent NULL representation; a missing function revocation still exposes default PUBLIC execute and fails comparison. It then verifies exact original receipt retries, rejected unauthorized reads and append-only mutations, enforced foreign keys/checks, and continued sequence allocation. Pending delivery/media leases must remain unavailable before expiry; after expiry, a fresh lease can resume the original payload while the old lease is rejected. This demonstrates logical content, access control and retry recovery, without sending an HTTP delivery.

All clients close before cleanup. Only the exact run-owned source/target databases and private archive directory are removed. A cleanup failure retains the private ownership file and reports its path for review; do not delete another run's metadata or blindly drop a database from a copied name. The public result contains aggregate checks, migration/script/archive hashes, archive size, timings and cleanup status. It contains no connection string, key, password or dump contents.

The local acceptance run passed with PostgreSQL 17.11: 25 canonical migrations, 48 tables and 23 synthetic records compared, including both JPEG stores and resumed retry state. Its 190,070-byte archive took 125 ms to dump and 267 ms to restore, with 1.59 s total runtime. These are small fixture observations, not production recovery or capacity targets. Both disposable databases were explicitly confirmed absent, and the private archive/directory were removed.

## What this does not recover

The configured runtime keeps its Guard records and both source/receiver JPEG byte arrays in PostgreSQL. Its runtime JSON, TLS private key/certificate chain, issuer private key, Auth API credentials, delivery destination credentials and APK signing keystore are separately supplied files or secrets. A database dump does not recover those materials. Android encrypted offline records also depend on their original installation/Keystore; this server drill does not export or restore a phone.

A future deployment needs an approved separate custody and recovery process for those exact keys/configuration, plus the selected Auth provider's own tested recovery process. Provider sessions and credentials are not portable merely because a Guard database has been restored. Restoring an old backup must not silently revive stale sessions, approvals or revoked keys. Review the original deployment marker, issuer/audience/public-key identity and current provider authority before service activation, and drain previous processes before changing deployment identity or restoring persistent state.

This drill is not a production backup service, offsite copy, point-in-time recovery, encrypted production archive, retention schedule, recovery-time objective or proof of complete Supabase-project recovery. Production storage/retention, provider recovery and external-key custody remain activation requirements. PostgreSQL explains that `pg_dump` exports one database and does not include cluster-global roles; its archive must contain the objects being restored. See [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), and [Supabase backup boundaries](https://supabase.com/docs/guides/platform/backups).
